# Правила репозитория

## Язык проекта

Используйте русский язык в общении по проекту, документации, комментариях к коду, сообщениях коммитов и описаниях pull request. Это правило распространяется и на ответы ИИ-ассистентов. Сохраняйте оригинальное написание команд, путей, идентификаторов API и обязательных служебных строк.

## Структура проекта

Приложение `printer3d` для 1С:Предприятие.Элемент расположено в `print_tech/printer3d/`.

- `Проект.yaml`: идентификатор, версия, русский язык разработки и режим совместимости (`10.0`).
- `Проект.xbsl`: заготовки обработчиков настройки приложения и миграции данных.
- `Основное/`: оболочка приложения и настройки интерфейса.
- `НСИ/`: справочники, перечисления, регистр совместимости принтеров и пластика. Размеры области печати — реквизиты справочника `Номенклатура`.
- `Производство/`: заказы клиентов, производство, регистры состояний принтеров, учёта заказов и загрузки оборудования.
- `Товародвижение/`: покупки, регистры покупок и остатков материалов в цехе и принтерах.

Метаданные хранятся в `.yaml`, программная логика — в сопутствующих `.xbsl`. Некоторые модули и файлы подсистем пока пусты. Отдельных каталогов тестов и ресурсов нет.

## Архитектура и границы реализации

Сверяйте метаданные со схемой `.local/inbox/Автоматизация цеха 3D-печати.drawio` и таблицей соответствия в `README.md`. При реализации этой схемы не добавляйте отсутствующие в ней документы без явного запроса пользователя. Принтер — позиция номенклатуры; материалы учитываются в граммах. Текущий этап — метаданные: движения, автоматические расчёты и синхронизация регистров ещё не реализованы.

## Сборка, проверка и запуск

В репозитории нет сценариев командной сборки, манифестов пакетов, настроек CI или средств запуска автотестов. Проверяйте и запускайте проект в среде разработки 1С:Предприятие.Элемент. Применимость npm, Make и инструментов классической 1С не предполагается.

Команды из корня репозитория:

```sh
git status --short       # Показать незакоммиченные изменения.
git diff --check         # Проверить пробельные ошибки в изменениях отслеживаемых файлов.
git diff -- print_tech/  # Просмотреть изменения приложения.
```

## Стиль кода и именование

Соблюдайте существующий формат YAML: отступы в четыре пробела, без табуляции; дефис элемента списка — отдельной строкой перед свойствами. Используйте содержательные русские имена, например `ТипыНоменклатуры`. Имя файла объекта должно совпадать со значением `Имя`. Размещайте связанные метаданные и модули в соответствующей подсистеме.

Сохраняйте существующие UUID в `Ид` при изменении объектов и реквизитов. Новым элементам назначайте уникальные идентификаторы. Явно указывайте ссылочные типы и допустимость пустого значения, например `Цвета.Ссылка?`. Не меняйте порядок свойств и режим совместимости без необходимости. Настроенных форматтеров и линтеров нет.

## Тестирование

Тестовый фреймворк и порог покрытия не заданы. Проверяйте изменённые метаданные в среде разработки и вручную выполняйте затронутые сценарии. Для справочников проверяйте создание, редактирование, ссылки и необязательные значения. В pull request указывайте выполненные проверки, результаты и оставшиеся непроверенными сценарии.

## Коммиты и pull request

Используйте короткие русские сообщения по образцу истории: `Исправлен порядок реквизитов`. Каждый коммит должен решать одну задачу.

В pull request описывайте изменение, затронутые подсистемы, связанные задачи при наличии и результаты проверок. Для изменений интерфейса прикладывайте снимки экрана; при изменении хранимых данных описывайте миграцию.

В коммитах с участием ассистента добавляйте соответствующую строку соавторства:

- Codex: `Co-Authored-By: codex <codex@openai.com>`
